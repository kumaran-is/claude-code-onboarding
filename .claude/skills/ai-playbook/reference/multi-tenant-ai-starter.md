# Multi-tenant AI Starter (governance §14.1 golden path, §8.1 controls)

A starter checklist for any AI feature that serves more than one tenant (organisation, customer account or product) from shared infrastructure: shared model gateway, vector store, agent runtime, memory, cache or traces. It adds no new rules. Each row points to the **canonical file** that owns the pattern, its code and its tests; read that file, do not copy from here.

**Status (honest):** this is a checklist that links to existing patterns, not a runnable scaffold. Publishing it as your organisation's *supported* multi-tenant starter, with an owning platform team and a review path, is an organisational decision (governance boundary C). A ticked row is not evidence; evidence is an executed test with its own exit code and a negative control (`ai-governance` Iron Law).

## When to use

- Any AI feature where a request from tenant A could reach data, tools, memory, cache entries or traces belonging to tenant B.
- Before the first production tenant is onboarded, and again when a shared component (cache, memory, new tool, new index) is added.
- Not needed for a single-tenant deployment with no shared store. Record that decision in the risk assessment (`factors.tenancy: single_tenant`).

## Rule zero: one source of tenant identity

The tenant id comes **only** from the verified credential (token claims or server-side session), is resolved once at the edge, and is passed as structured context to every layer. It never comes from the request body, tool arguments, retrieved text or model output. A missing tenant id fails closed with an error, never an unscoped query.

| 6 | Tool authorization by tenant | Tool receives the principal's scope, never a model-chosen one; the service re-authorizes the object | `.claude/skills/agentic-ai-dev/reference/tool-execution-safety.md` (scope injection); MCP servers: `.claude/skills/mcp-builder/` |

| 8 | Shared orchestration isolation | Per-invocation context object (tenant, user) passed to the agent run; no module-level state holding a tenant; checkpoints keyed by tenant + thread | `.claude/skills/agentic-ai-dev/reference/tool-execution-safety.md` (`RequestCtx` passed via `context=`); thread/session isolation tests: `.claude/skills/eval-guide/reference/golden-dataset.md` "Isolation, memory and side effects" |
| 9 | Cache isolation | Cache key carries tenant/ACL scope and model/prompt/corpus versions; semantic cache only for tenant-independent intents; embedding cache may be shared by recorded decision | `.claude/skills/agentic-ai-dev/reference/agentic-caching-patterns.md` (rules 3, 6–8; scoped key class) |
| 10 | Trace and audit isolation | Audit record per response with tenant, filters and chunk ids; no tenant or user ids in metric labels; trace access restricted per tenant (platform, C) | `.claude/skills/rag-security-reviewer/SKILL.md` "Audit log per response"; `.claude/skills/deployment-ci-cd/reference/ai-observability.md` (label rules) |
| 11 | Data-retention boundaries | Every stored item declares retention and expiry per tenant; nothing keep-forever | `.claude/skills/agentic-ai-dev/reference/agent-memory-lifecycle.md` §7 |
| 12 | Cross-tenant deletion propagation | Tenant-scoped erasure of every version from vector, keyword, metadata, object stores, caches and derived artifacts; plant → erase → probe | `.claude/skills/rag-security-reviewer/SKILL.md` "Deletion / right-to-be-forgotten"; `.claude/skills/agentic-ai-dev/reference/agent-memory-lifecycle.md` §7 |

Row 4 (database row isolation) is not a separate §8.1 bullet; it is how rows 2, 5 and 11 are usually enforced in PostgreSQL.

## Minimum tests before the first tenant goes live

Each test plants a distinctive string or id in tenant B and asserts it never reaches tenant A. Assert on tool arguments, retrieved ids, store reads and persisted rows, not on answer text.

| Test | Canonical definition |
|---|---|
| Cross-tenant retrieval returns no tenant-B id (and the same test fails with the filter removed) | `.claude/skills/rag-security-reviewer/SKILL.md` "Adversarial testing" (tenant-bypass probes) |
| Tenant isolation and session isolation eval cases | `.claude/skills/eval-guide/reference/golden-dataset.md` "Isolation, memory and side effects" |
| Cross-scope exfiltration red-team class | `.claude/skills/eval-guide/reference/red-teaming.md` (`cross_scope_exfiltration`) |
| Memory: cross-org planted string absent from rows, counts, k-NN, snippets, cached answers; missing org raises | `.claude/skills/agentic-ai-dev/reference/agent-memory-lifecycle.md` §12 tests 1–2 |
| Cache: tenant A cannot hit tenant B's entry | `.claude/skills/agentic-ai-dev/reference/agentic-caching-patterns.md` |
| Deletion: plant, erase, probe every surface | `.claude/skills/agentic-ai-dev/reference/agent-memory-lifecycle.md` §7 |
| Production canary: synthetic tenants probe isolation continuously; any violation pages | `.claude/skills/eval-guide/reference/red-teaming.md` (R4 probes) |

## Gaps (toolkit side)

- No single multi-tenant scaffold. `/scaffold-rag-pipeline` already generates a tenant-scoped `secure_retrieve` chokepoint and a tenant A / tenant B integration test (rows 2–3); `/scaffold-agentic-ai` does not generate tenant context, memory namespaces or isolation tests. Add those from rows 1, 5, 6, 8 and 9.
- Cross-product boundaries (row 7) and shared-orchestration isolation (row 8) have no dedicated pattern file; they reuse the tenant patterns with an extra scope key.
- Trace access control per tenant, gateway-level tenant policy and per-tenant quotas are platform controls (boundary C).
